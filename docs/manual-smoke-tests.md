# Staging/manual smoke tests — Combined Phase B

Run against the **operator-deployed staging revision**, not the production domain. Current testing origin: `https://duneandgrills-testing-six.vercel.app/`. Use dedicated test customers/staff, a test menu recipe/stock allocation, staged coupons/rewards and explicitly recorded test cash. Record revision, browser/device, actor/role, order number, time, expected/actual outcome and evidence. Do not use real card credentials or treat a placeholder gateway as a payment.

## Final acceptance flow

1. Customer opens `/menu` on a phone, searches/filters, customizes spice/add-ons and kitchen notes. Add items, refresh, confirm cart persists. Verify pickup has no delivery charge; delivery requires a valid address and configured minimum. Validate a valid/expired/ineligible coupon and eligible/ineligible reward. Log in with the same customer account that POS uses; also make a separate guest order.
2. Submit COD once. Capture order number and private tracking code from confirmation. Double-click or simulate a lost response; reconcile the original request. Exactly one order, one stock deduction and one coupon/reward use must exist. Guest tracking never places the private token in the URL and does not reveal contact/address/audit/payment internals to an unauthenticated caller.
3. Admin `/admin?tab=orders` sees the customer order and POS sees its own sale history. Cashier `/pos` opens/selects its terminal/shift, looks up the same customer, makes a customized pickup/delivery/phone sale, holds/resumes another draft and records actual cash/card-terminal/manual payment. Non-cash recording requires a real external reference. Repeated capture/reconciliation retains the original key and cannot double-stock/charge/award points.
4. Kitchen `/kitchen` receives both live online and POS orders in one queue, with source, fulfillment, notes/customization and server-based age. Exercise **New → Accept → Preparing → Ready**. Two devices racing the same transition must produce one accepted state and an honest no-op/conflict, never a skipped or reverted state. Change category/station filters and verify correct tickets.
5. For pickup/dine-in, complete handover. For delivery, dispatch then confirm delivered. Ready tickets remain until handover. Record actual COD collection via Admin/POS; verify completed but unpaid orders earn no points. Completing + paying earns eligible points once; repeating payment/handover does not award again. Delivery fee is not a points basis.
6. Customer `/profile/rewards` shows the updated balance/history/tier. Admin sales/channel/fulfillment reports include both sources and use the established financial/date basis. Partial/full refunds require the right role, record audit history, adjust points once (including spent-points debt) and restore stock only through the existing safe rule. Repeat refund/void requests and verify no double adjustment.
7. Disable network while menu is open. The offline banner appears; saved catalog is visibly stale. Reload `/menu`: generic offline page can show only the saved public menu. Staff reloads show generic fallback, never a cached staff session/queue/report. Orders, coupons, points, payments and kitchen transitions cannot be queued/sent offline. Cache Storage must contain no `/api/auth`, order/tracking, kitchen, POS, reward, customer or HTML/RSC response.
8. Reconnect. Kitchen/polling resumes promptly; stale status is revalidated. A failed SSE connection uses polling; restore SSE support and verify reconnection. Unknown sale/order outcomes are reconciled before creating a new request. Verify one final order/stock/points entry after recovery.
9. Deploy an approved *new staging build* while tabs are open. Expect update notification. With an active or saved unresolved order/payment, Apply update must be blocked. Finish/reconcile, save/hold edited drafts, then apply manually. Other tabs must receive a manual reload option rather than losing work automatically. Old `dg-pwa-*` caches disappear; unrelated origin caches remain.

## Install, kiosk and printer devices

- Android Chrome/Edge: open `/`, `/pos`, `/kitchen` individually; verify correct names, real branded icons and launch path after installation. POS/Kitchen launch requires valid role/session; locking/PIN and customer-display pairing still work. Verify browser and standalone fullscreen, touch actions, safe area and orientation at phone/tablet/desktop sizes.
- iPhone/iPad Safari: Share → Add to Home Screen, correct Apple icon, standalone launch, cart/account restoration, viewport and notification unsupported/denied messaging. Multiple apps from the same origin depend on OS/browser behavior; record actual results.
- Notification controls must ask only after clicking; denied permission must not repeatedly prompt. Hidden Kitchen tab receives a generic notification when allowed. Close all tabs: the app must not promise background push delivery.
- Pair `/pos/customer-display` with the cashier's display link in the same browser session. Verify only public bill data, clear/stale bill behavior on disconnection, no auth/cart API requests and no synchronization between unrelated sessions. A separate device requires an authenticated transport integration.
- Print/reprint from a sale and Admin order. Browser print dialog/PDF must render escaped notes, configured business identity, amounts/customization and duplicate label. Verify actual thermal printer paper width, margins, cut/driver behavior and bilingual text before production.

## Authentication/security

- Open/refresh `/pos`, `/kitchen`, `/admin` without cookies: login redirect, not 404. A forged cookie or forged `x-dg-path` cannot grant access. Customer/cashier cannot open Admin; Kitchen cannot collect payments. Accountant retains only its existing expense/record-search permissions.
- Revoke/deactivate staff and increment session version; API and fresh navigation fail closed. Simulate auth database outage: show recovery, retain saved work, do not silently become a guest. Restore network and retry. Failed logout must not claim that the server cookie was cleared.
- Cross-origin unsafe requests, wrong/missing CSRF and `$ne`/prototype payloads fail. Inspect production CSP/no-store/secure cookie/request-ID/rate/retry headers through the frontend domain. Rate-limit tests must use owned test traffic, never a load attack on the shared testing domain.
- `/api/readiness` returns transaction and index readiness. Confirm missing indexes produce 503 in an isolated rehearsal; never drop a staging/production index for testing. Confirm payment config advertises COD and rejects an unconfigured online provider.
- Inspect responsive overflow, keyboard focus, dialogs, form labels, screen-reader names/live banners, contrast, reduced motion and zoom. Automated local axe checks cover selected acceptance states; manually audit all checkout/refund/reward/held-sale dialogs and Safari/Android.

## Rollback and recovery

Rehearse backup/restore and index rollout on a separate DB. Roll back to the prior *compatible frontend/backend pair* using the provider's deployment controls; never delete request fences, points/refund history or reset order numbers. Existing API fields/status aliases remain supported. A rollback has a different worker version and prompts clients to reload safely. Run steps 1–8 again and record readiness/report totals before enabling traffic. Keep production credentials/domain/indexing separate until release sign-off.
