# Languages, points, delivery pins and scheduled orders

Source implementation and local verification: 16 October 2026. No cloud build, publication, deployment, paid-service activation, or live customer/order writes were performed.

## Enablement and configuration

The existing **Admin → Restaurant settings → Customer checkout** form configures the three new service policies. They default to **disabled** on existing databases. Saving unrelated settings does not enable them. Settings changes use the existing capability and audit log. There is no invented cash-conversion rate, service area, restaurant coordinate or scheduling capacity.

- **Points:** explicitly enter points per SAR of discount, minimum points, maximum SAR discount, coupon stacking choice, and approve proportional restoration on refunds before enabling. This conversion is separate from the existing earning rate. Discounts exclude delivery fees and cannot exceed the remaining merchandise subtotal. Requested points are validated, never silently increased or capped.
- **Delivery:** explicitly enter the restaurant latitude/longitude, circular service radius in km, and fixed SAR fee. The server computes distance and fee. When enabled, old saved addresses still load/edit but require a pin before delivery submission. When disabled, existing manual-address orders retain the existing delivery fee; coordinate-based service verification shows an unconfigured state. Pickup remains available. Clear the optional pin to use legacy manual delivery when area verification is disabled.
- **Scheduling:** verify existing weekly opening hours, preparation duration and Asia/Riyadh timezone; explicitly approve hours, slot interval, capacity per fulfillment type, booking cutoff and horizon (1–30 days). Overnight windows belong to their opening day. The first fulfillment slot is opening time plus preparation time; subsequent slots follow the configured interval. The last slot is no later than closing. Booking lead time is the greater of preparation time and cutoff. Slots are paged by local date in the app.
- **Language:** Profile offers العربية / English to guests and signed-in customers. Only `dg.language.v1` is persisted in ordinary storage. Changing language rerenders text, RTL content/navigation and directional icons without reloading or remounting customer state. Phone/email inputs retain LTR writing direction. Dates use Riyadh time and locale formatting; SAR and numbers follow the chosen language. Catalog names/descriptions accept optional `translations.ar` / `translations.en`, with original content used when missing/blank. Menu translation fields are additive and can be sent through existing authorized catalog APIs.

## Maps and native setup

SDK-57-compatible `react-native-maps` and `expo-location` are installed. iOS uses Apple Maps; Android uses Google Maps. Set the **public client key** `EXPO_PUBLIC_GOOGLE_MAPS_ANDROID_KEY` only if the owner has an approved Maps SDK project. Restrict this key to Maps SDK for Android, package `com.duneandgrills.customer`, and the actual signing certificate SHA-1. Do not put server credentials into Expo public variables. No Google project/billing/API was enabled by this work.

Foreground location is requested only on **Use my location**. Background location/service permissions are disabled. The app config adds the iOS purpose string and permits Android coarse/fine location. Generated native directories are not edited. A future native development/preview build is needed to include these modules and permissions in an installed binary; none was requested or run here.

Tapping the map or dragging its marker selects a pin. The coordinate fields also allow precise manual selection. Building, apartment/floor, landmark, delivery instructions and contact phone are saved with the address and copied into the immutable order snapshot. GPS denial/failure/timeout, missing Android key, web preview and map-load failure retain the form and offer manual entry/pickup. No geocoding provider is required or called. Address text remains editable independently of the pin. Existing coordinate-free addresses remain readable.

Official references used: [Expo SDK 57](https://docs.expo.dev/versions/v57.0.0/), [maps](https://docs.expo.dev/versions/v57.0.0/sdk/map-view/), [location](https://docs.expo.dev/versions/v57.0.0/sdk/location/), [runtime localization and Router direction](https://docs.expo.dev/guides/localization/).

## Server contract and lifecycle

- `GET /api/orders/config` adds public `checkout` policy and restaurant timezone, retaining old fields.
- `GET /api/orders/slots?type=pickup|delivery` returns enabled state, timezone and available ISO instants. It is advisory; capacity/time are rechecked during creation.
- `POST /api/orders/quote` resolves current catalog prices, coupon, points policy/balance, service area/fee and slot eligibility. It returns separate coupon/points discounts, fee and total without reserving resources.
- `POST /api/orders` accepts optional `pointsToRedeem`, `scheduledAt`, `reviewedTotal`, and `customer.deliveryDetails`. Existing API consumers can omit them. New mobile requests bind the reviewed total so price/fee changes require review. Client-supplied prices, discounts and delivery fees are ignored.
- The existing order/inventory/coupon transaction also reserves slot capacity and debits the **same existing points balance/ledger**. Reservation and deduction commit with the order, so failed creation leaves no abandoned points reservation. Conditional balance updates serialize against concurrent reward redemptions. The existing request fence guarantees retries never spend points or capacity twice. Quote failures do not create a pending order.
- Cancellation/failure returns all redeemed points and releases its slot once in the same lifecycle transaction. Refunds use the administrator-approved proportional rule: cumulative returned points are `floor(pointsSpent × cumulativeCashRefund / originalCashPayable)`, capped at the original spend. Full cash refund returns all redeemed points. Existing points debt is settled first, matching reward-return behavior. Earning continues to use discounted merchandise spending and the existing completed-and-paid policy. REDEEM/REVERSAL entries appear in the existing points history.
- For orders fully covered by points with zero cash payable, the existing restaurant refund panel offers **Request points restoration**. It uses the same approval/completion workflow with an explicit `pointsOnly` flag, a separate transactional reservation, and no cash movement. Concurrent requests, rejected/cancelled requests and repeated completion cannot restore the same points twice. Ordinary cash refunds still require a positive amount.
- Scheduled orders store fulfillment time and `kitchenReleaseAt = scheduledAt − preparationMinutes`. The **existing kitchen queue polling** releases tickets by this server-time predicate; no external cron or client timer is required. The transition engine prevents preparation/handoff before release, including admin calls. Preparation due time uses the stored fulfillment time. The operational pending-age clock starts at release rather than advance booking. Orders remain visible in restaurant management before release, with their scheduled time. Customer confirmation/history/tracking and kitchen cards show the scheduled time. Existing immediate orders are unaffected.
- Active assigned riders receive the saved pin/details through their existing authorized detail response and can navigate to the coordinates. Historical recipient privacy remains unchanged.
- The protected pending payload retains address details, schedule, points intent, reviewed amount, original account/origin and idempotency key. Unknown outcomes block new requests/account switching. If a slot, points policy or price changes, use the existing check/cancel flow before reviewing a new request. No changed request is sent under the original key.

## Persistence and compatibility

All fields are optional/additive. No bulk data migration or live backfill is needed. Existing settings read new disabled defaults; existing orders retain immediate fulfillment; old addresses retain their original text. `OrderSlot` uses its unique string `_id` as the permanent capacity bucket; cancellation decrements rather than deleting it. Future bookings reserve inventory using the existing order engine. MongoDB replica-set transactions remain required, as before. Normal model initialization creates the additive indexes/collection; production rollout is outside this source task.

## Local verification

- Mobile: `npm test` (75 passing), `npm run typecheck`, `npm run lint`, SDK-compatible dependency check, and Android/iOS Hermes + web exports.
- Backend: checkout policy tests; isolated checkout lifecycle tests covering concurrent points/slots, idempotent replay, original request reconciliation, coupon integration, cancellation, partial/full refund, old/manual/guest addresses, saved pin CRUD, out-of-area/past-time rejection and kitchen release. Existing unified order engine, native authentication/proxy, settings, kitchen, operational dashboard and rider workflow regressions were also run against helper-owned loopback replica sets.
- Frontend: lint and selected admin/order/rider tests, including validated-pin navigation with legacy address fallback.
- `tests/checkout-smoke.cjs`: actual screens in the existing isolated protected-storage harness at 320/390px. Arabic/English persistence, RTL navigation and phone direction, denied location, web map fallback, old saved address, out-of-area correction, combined coupon/points/schedule review, lost order response, immutable retry and safe cancellation were checked. All API requests are intercepted. Screenshots are ignored local artifacts under `mobile/artifacts/`.
- Arabic Home, Menu, Offers, Cart, Orders, Points, Addresses and Authentication screens also receive browser rendering/viewport checks. Arabic and Persian numeric keyboard input is normalized for phone, points and coordinate validation.
- Existing browser checkout smoke verifies menu/cart/customization/navigation drafts/coupons and the native secure-storage send gate. No real service or customer data is used.

The mutable locale presentation boundary opts out of React Compiler memoization using its documented `use no memo` directive so translations/formatters update on language changes. Customer state, network and persistence logic retain their existing behavior.

**Limits:** native device/emulator execution, native map tiles/dragging, real GPS, OS permission prompts, secure-storage lifecycle and installed-app RTL gestures are not proven by JavaScript exports or browser fixtures. No new APK/IPA was built. Dependency audit still reports 30 upstream advisories (11 moderate, 19 high); incompatible forced upgrades were not applied. Restaurant policy values and an approved Android map key must be supplied by the owner before enabling those services.
